### 翻车：主键不自增

新表用 `BigInteger` 当主键，SQLite 上它不是 `INTEGER PRIMARY KEY`，自增失效，9 个测试齐刷刷
`NOT NULL constraint failed: intent_usage.id`。改用 `app/models/base.py` 里现成的
`BigInt = BigInteger().with_variant(Integer, "sqlite")` 才对。这条坑 ch02 就踩过，我这次又踩了
一遍——因为写新模型时照着 DDL 的 BIGINT 直译，没看 base.py。

## T3 evidence_confidence 正式闸 + 阈值校准

公式落在 `app/agent/gate.py`，纯函数，权重写死并注明「不做拟合」：

```
confidence = 0.60*top1 + 0.25*min(有效/3,1) + 0.15*min(分差/0.30,1)
```

`check_gate` 传了 `min_confidence` 就比 confidence，不传退化成 ch04 的只比 top1——
留这条路是因为老调用方和 9 条老单测都按旧行为写的，一次改干净反而不好定位问题。

### 校准结果（`reports/ch09_gate_calibration.md`）

- 76 条用例（正例 62 含噪声变体 / 负例 14 = D 桶），真实 hybrid_rerank 检索，**跑了 22 分钟**
  （76 次 CPU 重排，别在赶时间的时候重跑）。
- 选定 **0.45**：正例误杀 6.5%（4/62）、负例拦下 78.6%（11/14）。
  0.53 能拦到 85.7%，但误杀涨到 11.3%，超过「误杀 ≤10%」的红线。
- **被误杀的 4 条全是噪声变体**（错别字「快回一下」、型号写法不同），31 条干净题零误杀。
  这条事实要记住：闸对拼写不鲁棒，但根子在检索那一段——带上噪声变体后检索本身就给不出高分。
- 漏放的 3 条负例都是 near 型（W60 碳板第几代、LP300 对比德龙、W40 宽楦楦宽），
  confidence 0.53~0.80。这类「库里有相邻事实但没有答案」的问题，光看检索分数分不开，
  得靠第二层自评——也就是为什么闸必须两层。

### 翻车：值写回了 state，读的时候 KeyError

`confidence_gate` 节点无条件返回 `gate_confidence`，但 `AgentState` 没声明这个键，
LangGraph 按 schema 过滤后值就丢了，测试 `out["gate_confidence"]` 直接 KeyError。
「写回失败」的报错长得像「节点没跑」，实际是 TypedDict 少一行。

## T4 飞轮流水线：标准化 → 规则查重 → 模型查重 → 归并落点

- 规则查重（规范化后相等 / 互相包含且长度差 ≤40%）在前，模型查重在后。
  理由有实测支撑：池子里 39 行只有 13 个不同问题，这类重复用字符串就能认出来，不该花模型调用。
- 模型给了不存在的 `matched_id` 一律按未命中 + degraded：归并指向空处比不归并更糟。
- 模型查重失败（upstream 502 / 坏 JSON）也按新建处理但计入 `failed`——
  「没判成」不能被当成「确认是新缺口」悄悄放过。
- `scripts/run_flywheel.py --batch N [--dry-run] [--since-id]`。

### 返工：dry-run 那版是假的

第一版写成「照常 create，然后 rollback」，但 `review_repo.create` 内部已经 commit 了，
rollback 抹不掉——预览会真的往库里塞行。改成把 `dry_run` 传进 `dedupe`，让「该新建」那条路径
根本不落库。教训：**别拿事务回滚当预览**，写路径自己得支持只算不写。

## T5 审核通过 = 走 ch03 双写

- `vectorize_pending(session, store, embedder, ...)` 从 `build_index` 里抽出来，建库和审核调同一个。
  复制一份到飞轮里的后果是可预见的：迟早出现「MySQL 有行、向量库里没有」的块。
- `approve()`：按 (分类, 问法) 找已有块 → 有就改答案并**退回 pending**（向量里是旧文本，
  不重算等于改了个寂寞），没有就新建 → 向量化 → 状态置通过。
- `reject()` 只改状态。驳回通常意味着「这不是知识缺口」，写进库里只会污染检索。
- `scripts/review_cli.py list|show|approve|reject`：没浏览器时的可用路径，`show` 会把原话与快照一起打出来。
- 抽出 `vectorize_pending` 之后 `build_index` 的中断演练仍然过（计数搬进 report 再抛异常）。

### 这一圈里踩到的三个坑

1. **老库不跟着模型变**：三张新表是修 `BigInt` 之前建的，SQLite 里落成 `id BIGINT NOT NULL`，
   飞轮一跑就 `NOT NULL constraint failed: review_queue.id`（`create_all` 只建不存在的表）。
   处理：先断言三张表都是 0 行，再 drop 重建、重跑 `migrate_ch09.py`，主键变成 `INTEGER`。
   **给以后的自己**：改完模型要顺手确认老库结构，别指望建表语句自动迁移。
2. **Milvus Lite 不能被同一进程连两次**：审核通过第一版自己 `new MilvusStore()`，
   直接 `Fail connecting to server on 127.0.0.1:58107`——Lite 是嵌入式单实例，检索器那份已经占着。
   改成复用 `get_default_retriever()` 的 store/embedder，顺带省掉第二份 2G 的 BGE-M3。
3. **`_index_assets` 第一次写成 lru_cache 的「没人审核就不加载」**：方向对，但第一次请求时才发现
   撞了上面那个坑，报错栈里显示的是新代码（traceback 读的是磁盘上的当前文件），差点误判成"新代码有问题"。

### 顺带补的

- `gate` 事件的 SSE 载荷加了 `confidence`（原来只下发 `top_score`，前端/脚本看不到新口径的分数）。
- `AgentState` 补 `gate_confidence` 声明——不加就 KeyError，见 T3。

## T10 收尾补做：Langfuse 接入（需求 1 + 2）

Cloud 免费层（Hobby）为主，自托管 compose 只做文档备选（本机 Docker daemon 没起，没真跑过）。
入口文件 `app/observability/tracing.py`，聊天链路只在 `agent_chat.py` 的 astream 块多包一个
上下文管理器，旁路性质。

### 实现要点

- **四种降级全部返回空 callbacks**：`LANGFUSE_ENABLED=false` / key 缺失 / SDK 导入失败 /
  host health 检查不通。工厂按 lru_cache 缓存，**缓存键带上配置本身**——测试里改 settings
  不会读到上一件的缓存。任何初始化失败只记日志，不抛异常。
- **一轮对话一条 trace**：根 span `chat:{conversation_id}`，`langfuse_session_id` 归组。
  上下文必须包住 `async for` 循环而不是包函数——astream 是异步生成器，图在迭代时才执行。
- **意图/路由补写**：`intent` 事件到达时写根 span 的 trace 元数据；拒答轮打 `abstain` tag。
- **检索 span 手动包**：SDK 的 LangChain 集成只覆盖 LangChain 世界，检索是自己的代码，
  用 `observe(as_type="retriever")` 包 `retrieve`——答不上问题时最该看的就是这一环。

### 翻车与返工（这轮的主要收获）

1. **pip 装到 5.0.4，不是以为的 v3**。教程里的 v3 API 几乎全不存在：没有
   `update_current_trace`，`CallbackHandler` 也不再吃 secret/host（只收 public_key，其余走
   client 构造参数或环境变量）。**教训**：「以所装版本官方文档为准」不是口号——v5 是 OTel
   底座，trace 级属性就是根 span 上的 `langfuse.trace.metadata.*`，由 `propagate_attributes`
   写；补写入口因此改成 `use_span(根 span)` + `propagate_attributes`，保证落点在根上而不是
   此刻恰好活跃的某个节点 span。
2. **后台 pip install 被沙箱守卫杀死**（sitecustomize SystemExit:1，包没装上还看不出）。
   带 `dangerouslyDisableSandbox` 重装才成。教训：装依赖别放后台。
3. **otel 版本冲突警告**：chromadb（本机另一个项目的依赖）拽着
   `opentelemetry-exporter-otlp-proto-grpc 1.39.1`，与 langfuse 要的 1.45.1 不兼容。
   判定惰性——本项目不走 grpc exporter，requirements.txt 只 pin 用到的那些。
4. **测试断言找错 span 名，一度误判成 SDK 缺陷**：`_traced` 给检索 span 显式起了名
   `rag.retrieve`，测试却按函数名 `stub` 找，0 条。当时先入为主归因成「observe 走 keyless
   `get_client()`，多实例时返回禁用 client」——读源码确认 keyless 单实例是正常返回的，
   实例数打印出来只有 1 个，才回头核对名字。**教训**：断言失败先打印实际值，别顺着上一个
   假设编故事。
5. **`langgraph_node` 元数据是 JSON 编码字符串**（`'"classify_intent"'` 带引号），直接比集合
   比不中，`json.loads` 解包后再比。
6. **测试里给 `graph_module.retrieve` 直接赋值会污染其他测试**，改 `monkeypatch.setattr`。
7. **全文件首跑疑似挂死**（300s SIGTERM、管道缓冲无输出）：单跑每个用例都 4-6 秒。
   修完上述问题后重跑，14.5 秒全过——大概率是失败用例的 SDK client 没清干净拖住了进程退出，
   没有最终定论，记下来。
8. **用户按 SDK 文档把 host 写成 `LANGFUSE_BASE_URL`，被静默忽略**（2026-10-23 实测时发现）：
   配置只认 `LANGFUSE_HOST`，`.env` 里那行等于不存在，host 回落默认 EU 端点——而账号在美区，
   key 到错大区直接鉴权失败。已改 `AliasChoices` 两个名字都认。**教训：用户会按官方文档的
   变量名写配置，只认一个名字就是给未来埋雷；这种"配了却不生效"必须靠双名字或显式告警堵住。**

    observation 数不变（67 → 67），耗时无差异。
- **读云端要用 v2 端点**：`/api/public/traces` 与 `/api/public/metrics` 在这个服务版本
