## 2026-10-20 21:5x 开工:先看清 CH05 留了什么坑

### 用户关键原话

- "我要用 Superpowers 模式把客服系统里占位的分流器做成正式版,这是 Workflow 里最关键的节点。"
- "意图识别用 LLM prompt 路线,不训分类模型,prompt 按四件套写:枚举成选择题 / 强制 JSON 只给 intent 和 confidence / 边界 few-shot / 留「其他」兜底"
- "槽位处理:缺订单号不让模型猜,执行阶段弹订单选择器让用户点选回填;退款原因不追问,提交时从固定类目里选"
- "本章不做:微调小模型 / BERT 做意图分类、跨会话记忆"

### 开工前的事实核对

- `app/agent/intent.py` 是 CH05 留的七类 + 四出口,`route` 只有 knowledge / business / complaint / chitchat。本章要加第五个出口 `refund`(退款退货、售后走确定性���流程),**七类不改,出口五类**,所以表不用重画,只加值。
- `app/agent/graph.py` 的 `resolve_reference` 节点是占位(原样返回),本章换成真的 `understand_query`。
- CH05 的 `.env` 里 `LLM_MAX_TOKENS=512`。指代消解和意图识别都是短 JSON,512 够;但退款子流程要把「订单事实 + 政策条款」塞进 Agent,输出容易超——这条在验收时要盯。

### 纠偏了什么

没有为「指代消解」和「Query 改写」写两次模型调用。需求第 1、2 条是两件事,但读的是同一份上下文:分两次调,两次对「用户在说什么」可能得出不同理解,于是检索按一个意思走、回答按另一个意思走。合并成一次调用、一份 JSON 输出(`resolved` / `canonical` / `order_id` / `changed`),两处共用。

### 两个刻意的设计取舍

1. **问题完整就原样透传**(`changed=false`)。改写不是目的。为了让日志好看去揉一句本来就好的问题,检索效果通常更差,还多一次幻觉机会。
2. **订单号让模型抽,正则只兜底**。模型从一句话里抽结构化槽位比正则稳;但模型挂掉时链路不能断,所以 `guess_order_id` 从 `resolved` 里再捞一次——`resolved` 是补全后的句子,历史里的单号已经被补进去了。

### 翻车

**`prepare_refund` 的单测打到了真 Milvus**,报 `faiss::FileIOWriter could not open autoindex.idx`。原因:`refund_flow` 里自己 `from app.rag.retriever import retrieve`,monkeypatch 只替换了 `app.agent.graph.retrieve` 那一份引用,子流程用的是另一份。以后 patch 检索必须把 `app.agent.refund_flow.retrieve` 一起换掉。同类问题在 `test_stream_accepts_order_id_slot` 上又出一次,一并处理。

## 2026-10-20 22:3x 第二块:图接子流程

### 关键产出

- `graph.py` 节点从 9 个变 10 个:`resolve_reference → classify_intent →(条件边)retrieve_knowledge → confidence_gate → agent/abstain ｜ refund_subflow →(条件边)agent/abstain/log_trace ｜ complaint_reply ｜ chitchat_reply → log_trace`。

- `route_after_intent` 多一条 `refund` 分支;`route_after_refund` 三出口:有事实且过闸 → `agent`,证据弱 → `abstain`,缺订单号 → 直接 `log_trace`(回订单卡片,不进模型)。
- `app/services/agent_chat.py` 新增 `resolved`、`order_options` 两种 SSE 事件,`chat_with_agent()` 收 `order_id` 参数(用户点选的订单回填进来)。
- `app/api/routes.py` 新增 `GET /refund/reasons`(固定类目)、`POST /refund/apply`(受理即建「售后」工单,工单号当受理号)。
- 意图升八类连带改测试:`test_seven_intents_map_to_four_routes` → `test_eight_intents_map_to_five_routes`,退款退货 route 从 business 变 refund,兜底从业务类变「其他」。

### 为什么退款子流程的顺序写死

「先订单、再政策、最后让 Agent 判断」这段编排**不由模型决定**。退款判错一次的代价是赔钱加纠纷,而它需要的信息永远是固定两样(这单是什么、政策怎么规定)。确定的事交给确定的编排,Agent 只负责最后那句需要理解力的判断。这跟 CH05 让 Agent 自己决定调什么工具不矛盾:那里是查询,错了重查一次就行。

## 2026-10-21 验收阶段

见下方各节。

### 验收 1、2:多轮对话 eval

单测只能验解析层,「每一轮意图都判对、指代都补全对」必须真模型跑标注样例。新增 `tests/eval/run_dialogue_eval.py`,复刻图的前两个节点(`understand_query` 带历史 → `classify_intent` 判补全后的问题)。

历史怎么造是这一节的取舍点:**用户消息用原话,客服回复用一句不含信息量的占位话术**。真链路上客服回复里当然有单号、有商品名,拿它当提示等于给模型递答案,测出来的数字不作数。这样指代只能靠用户自己说过的话补全。

结果(见 `reports/ch06_dialogue.md`):

| 指标 | 结果 | 阈值 |
|---|---|---|
| 多轮意图判对 | **16/16 = 100%** | 90% |
| 指代补全对 | **8/8 = 100%** | 90% |
| 怪问题落「其他」 | **5/5** | 全中 |

典型补全(都是模型自己补的,不是正则):

- 「那它能退吗」→「订单 1001 能退吗」
- 「那这东西现在到哪了」→「订单 1001 的物流到哪了」
- 「这个能七天无理由退吗」→「订单 1005 买的东西能七天无理由退吗」
- 「我申请售后了,进度查一下」→「我申请售后了,订单 1007 的售后进度查一下」

### 一次标注返工

第一版 5 条怪问题里「你觉得我该买哪双」标的是「其他」,模型判成「商品咨询」,我判它错。回头想是**我标错了**:求推荐是商品相关的咨询,判「其他」反而是错的——「其他」是给判不出来的问题兜底,不是给「我不喜欢的问法」兜底。

改了两处:这条改标「商品咨询」,并额外加一条真正的域外问题「帮我写一首关于秋天的诗」保持 5 条兜底用例。eval 脚本也随之分两组:**期望「其他」的进怪问题组(验兜底)**;**期望别的进意图准确率(验不要滥用兜底)**。混在一起算会把「兜底滥用」这个错误藏起来。

同一类问题在 CH05 的旧用例上也出现一条:「你们这个会员怎么办」当初七类时被迫标成「闲聊」,八类后模型判「其他」——**模型对、标注错**。改标并写了原因。重跑 `run_intent_eval` → **38/38 = 100%**(`reports/ch05_intent.md`)。

## 2026-10-21 验收 3、4:真模型 + 真 Milvus 全链路

**验收 3**(同一会话两轮,`s-c3v2`):

| 轮次 | 原话 | resolved | canonical | intent / route | 闸 |
|---|---|---|---|---|---|
| 1 | 订单 1003 的物流到哪了 | 原样透传(`changed=false`) | 订单 1003 的物流进度 | 物流 / business | — |
| 2 | 这个能退吗 | **订单 1003 的包裹能退吗**(`changed=true`, order_id=1003) | 订单 1003 的退货条件 | 退款退货 / **refund** | passed=true, top_score 0.7227 |

第 2 轮的答复把两边都吃到了:先报「订单 1003 大容量双肩通勤包 ×1,实付 ¥159.00,运输中」,再按政策条款答「签收 7 日内、符合完好标准可退;质量问题不受 7 天限制」并挂 `[1][2][7]` 角标,最后根据自己的物流事实给建议「包裹还没签收,建议签收后再确认」。

**验收 4**(不带订单号,`s-c4v2`):发「我要退货」→ `order_options` 事件下发 3 张订单卡片(1009 / 1018 / 1005),`finish_reason=need_order`,同时吐一句要用户点选的话术。带 `order_id=1018` 重发 → 走完子流程,`gate passed top_score=0.7699`,`done.actions=[apply_refund]`,答复先报订单事实再追问「质量问题还是无理由」「吊牌是否完好」——需求第 6 点「需求澄清留在主力 Agent 里」是对的。

提交退款单 `POST /refund/apply` → `refund_no=T202610200002`,`tickets` 表落一行「售后 / 订单 1018 申请退款,原因:质量问题」;`messages` 表三轮 user/assistant 顺序正确。

### 这一节抓到两个真 bug(单测全绿也照样漏)

1. **`'HumanMessage' object has no attribute 'get'`** —— `classify_intent` 里把 history 当 dict 取。真链路上 history 是 `trim_history` 产出的**消息对象**,只有 eval 和单测喂 dict,所以 306 条单测一条都没拦住,首个多轮请求直接 500。
   修法:把历史渲染抽成 `query_understanding.history_text()`,两种形态都认,意图与指代共用一份。补回归测试 `test_history_accepts_langchain_messages`。
2. **跨轮 State 残留** —— checkpointer 按 `thread_id = conversation_id` 保留 State,下一轮只覆盖输入那几项,于是**上一轮的 `order_options` 和 `finish_reason` 漏到本轮的 done 事件里**。现场表现:本轮闸没过走了拒答,前端却既弹拒答话术又弹上一轮的订单卡片。
   修法:服务层 `_TURN_RESET` 每轮显式重置本轮字段。放服务层不放节点里——节点只对自己写的字段负责,「一轮从哪开始」是服务层的知识。补回归测试 `test_second_turn_does_not_inherit_previous_turn_state`。

两个 bug 有共同点:**都是「只有真跑多轮才暴露」的时序/形态问题**,假模型单测按构造不会走到。这就是提示词要求「跑一遍真链路」的价值。
