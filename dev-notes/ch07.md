## 2026-10-21 开工与 spec 定稿

### 用户关键原话

- "让客服在一通会话里记得住前面聊过什么,把第一版的简单裁剪升级成正经的上下文管理。只管当前会话,不跨会话、不存用户画像。"
- "最近的留原文,一个字都不压;中间一层按规则截短,用户原话不动、客服答复只留开头几十个字、大块工具结果换成一行标识;最远的异步压成一段段梗概。两个锚点划边界……降级只挪这两个 id、不搬数据。"
- "触发看用量不数条数,工具结果压根不落消息表,数条数看不见它涨。"
- "梗概不许单独占一条 system,上游模板会把所有 system 上提合并渲染,工具定义被挤到可变内容之后,前缀缓存整段作废。"
- "token 预算从模型窗口倒推,不写死成常量……中文按字数折 token 的口径要和预算一起校准,只改一个净效果是反的。"
- "装得下就不压,压缩是成本不是美德,这一条也要验。"

### 关键产出

- Spec:`docs/superpowers/specs/2026-10-21-ch07-context-management-design.md`(D1-D8)。
- 计划:`docs/superpowers/plans/2026-10-21-ch07-context-management.md`(T1-T7)。

### 开工前的一个实测,直接改了 D5

先量了一下项目现状:
- `build_agent_system_prompt(max_steps=3)` 是 1061 个汉字;
- `count_tokens_approximately` 对这个提示词报 **5305 tokens**——五倍。

原因是这个函数按英文 BPE 口径数中文。CH01 起 `trim_history` 就一直用它,等于实际预算被砍到五分之一(配 2048 的预算,真实只装了约 400 token)。这个错误一直被「历史不长」掩盖,本章预算要按 token 倒推,不校准就是全线算错。

所以 D5 改成自己写 `estimate_tokens`:汉字与全角标点按 1 token、其余 4 字符 1 token。这个口径对 DeepSeek 偏保守(它的中文大约 1 字 0.7~1 token),保守方向放在预算上是对的——估多了只会少留一点历史,估少了会 400。

### 纠偏了什么

第一版想把摘要直接写进 `messages`(一条 assistant 消息塞梗概)。否掉的理由是需求原话:**梗概单开一张会话摘要表,不塞进逐条消息里**。塞进消息表的坏处是「原文」和「梗概」混在一条流里,前端回载历史时用户会看到一段不是自己说过、也不是客服说过的话。

## 2026-10-21 T1 预算:先量口径,再写公式

### 关键产出

- `app/core/token_budget.py`:`estimate_tokens`(汉字 1 token、其余 4 字符 1 token)、`ContextBudget`、`compute_budget` / `budget_from_settings` / `log_startup_check`、`tool_schema_tokens`。
- `app/config.py` 五个预算输入(`MODEL_CONTEXT_WINDOW` / `MAX_OUTPUT_TOKENS` / `MAX_USER_INPUT_TOKENS` / `TOOL_RESULT_MAX_TOKENS` / `RERANK_TOP_K`)+ `LAYER2_ASSISTANT_HEAD` + 摘要开关。
- `tests/test_token_budget.py` 11 条,含「演示配置能否复现需求里那组数」。
- 启动自检接进 `app/main.py` 的 lifespan。

### 一个反直觉的量,直接决定公式对不对

`build_agent_system_prompt(max_steps=3)` = 1061 汉字。`count_tokens_approximately` 报 **5305**,五倍——它按英文 BPE 数中文。用它的项目(包括 CH01 起的 `trim_history`)实际只装了配置的 1/5 历史,只是历史一直不长所以没人发现。

自己写 `estimate_tokens` 之后:1061 汉字 → 863;5 个工具定义 349 token(加 `{"type":"function",...}` 包装 8/tool → 397)。两笔加起来 1260,演示配置下算出:

```
window=18000 history=5640 layer1=3947 layer2=1693
```

需求里写的是 `5650 / 3954 / 1695`——差 9~10 个 token。**差在 system prompt 与工具定义的实测字数上**(需求那组按它自己的提示词量的),算式结构一致:层 1 取七成向下取整,层 2 = 总量 - 层 1(各取三成会让两个数加起来比总量少 1~2)。这条差异我留在测试里当近似断言,并写进本节,而不是把常量反标定到 5650——那样得到的「精确」是假的。

### 纠偏了什么

第一版没把工具定义算进固定开销。需求第 3 点把「system 人设、红线和工具定义」算作每轮不变的那一段(它们是前缀缓存的对象),不算进去就是自欺:5 个工具占小窗口配置里历史预算的 7%。补上之后才落到 5640 这个数。

## 2026-10-21 T3 三层切分:边界先定死,再做功能

### 关键产出

- `app/core/context.py`:`HistoryItem`(消息带 id 才能比锚点)、`plan_layers()`(按锚点切 + 层 1 降级 + 层 2 丢弃)、`render_layer2()`(按角色截短)、`assemble_messages()`(固定顺序)、`render_model_ctx()` / `render_history_ctx()`(需求 6 的两个必打日志)。
- `tests/test_context_layers.py` 15 条:锚点为 0 等于全给层 1、两锚点切三段、摘要覆盖段不发、层 1 降级挪最早、层 2 超预算丢最早、用户原话一字不动、工具结果换一行、拼装顺序、空背景块跳过、两处 ctx 日志,外加 4 条工具配对。

### 几个定下来的边界

**锚点为 0 不等于「全在层 2」,等于「还没有降级过,全在层 1」。** 需求里「装得下就不压」全靠这条:新会话两个 id 都是 0,如果按 `id < layer1_from_msg_id` 切,层 1 恒空、层 2 装全部,一开口就触发摘要。

**降级只回写 `layer1_from_msg_id`,不动 `summary_upto_msg_id`。** 两个锚点各管一段:前者管「层 1 从哪开始」,后者管「摘要覆盖到哪」。同时推会让被降级但还没压成梗概的消息直接消失。

**层 2 里 tool 角色一律不留。** 具体见 T5 的 400 事故,这条是踩出来的,不是设计出来的。

## 2026-10-21 T4 后台摘要:看用量、只追加、不阻塞

### 关键产出

- `app/services/summary_service.py`:`should_summarize()`(纯函数,单测直接打)、`run_summary()`(自己开 session → 取区间 → 压 → 落库 → 推两个锚点)、`schedule_summary()`(`asyncio.create_task`,返回 Task 只为单测能 await)、`SUMMARY_PROMPT`(四类事实 + 四条硬约束)。
- `tests/test_summary_service.py` 8 条:装得下不压、超预算才压、区间取 `summary_upto+1 ~ layer1_from-1`、只追加不改旧段、锚点同步推进、模型报错只记日志、空返回不落库、总开关关掉直接跳过。

### 为什么触发判据必须用「截断前的层 2 用量」

第一版 `LayerPlan` 只有 `tokens_layer2`(截断后)。`should_summarize` 拿它去比预算,永远等于「刚好装得下」,于是**一次都没触发过**。真正的用量是截断前的 `tokens_layer2_raw`:层 2 超预算被丢掉的消息,正是该压成梗概的那批。补了这个字段,触发器才响。

### 纠偏了什么

第一版想给摘要加「按条数也算一次」的兜底(比如每 20 条压一次)。删了。需求原话是「触发看用量不数条数,工具结果压根不落消息表」——按条数兜底等于在错误的判据上再加一个错误判据,而工具结果恰恰是数条数看不见的那部分。

## 2026-10-21 T5 接进图:三个真 bug

### 关键产出

- `AgentState.messages` 挂 `add_messages`(需求 5「完整历史靠 checkpoint」),`summary: str` 走字段;agent 节点只返回本轮新消息,其余四个终端节点各补一条 `AIMessage`(否则 checkpoint 里的历史缺客服那一半)。
- `app/services/agent_chat.py`:`_plan_context()`(切层 → 读梗概 → 算预算 → 推进锚点 → 打 `history_ctx`)、`_schedule_summary()`。
- `app/agent/react.py`:改用 `assemble_messages()` + `plan_from_history()`,每轮打 `model_ctx`。
- `tests/test_context_wiring.py` 5 条。

### bug 1:上下文拼出孤儿 tool 消息,上游 400

45 轮压测里出现 4 次 `UPSTREAM_ERROR`:

```
openai.BadRequestError: Error code: 400 - {'error': {'message': "Messages with role 'tool'
must be a response to a preceding message with 'tool_calls'" ...}}
```

根因:三层切分把一对「助手发起工具调用 → 工具结果」切到了不同层。层 2 里那条 assistant 被截成纯文本 `[发起工具调用 query_order]`(没有 `tool_calls`),层 1 开头就剩一条孤儿 tool 消息。CH07 之前不会出现,因为历史从不跨层。

修法分两步,缺一不可:
1. `render_layer2()` 里 assistant 一旦被截成纯文本就**丢掉 `tool_calls`**;tool 结果不再保留 `ToolMessage` 角色,改成一句普通 ai 消息 `[工具结果 N 字,已省略]`。
2. `assemble_messages()` 末尾统一过一遍 `sanitize_tool_pairs()`:配对不全的 assistant 退回纯文本、孤儿 tool 丢弃。

只做第 1 步不够——第 1 步之前我先只加了 `sanitize_tool_pairs`,它看到层 2 那条 assistant 还带着 `tool_calls`、后面紧跟配对的 tool,判成「配对完整」原样保留,而上游照样 400:层 1 那半早被切走了,它认为完整的这一对其实指向的是另一个位置。**判据要按最终发出去的样子算,不能按中间态算。**

### bug 2:层 1 只挪一条,摘要永远不触发

原来降级循环是 `while tokens_layer1 > layer1_budget`,超一点挪一条就停。结果是层 2 长期只有 0~2 条、`tokens_layer2_raw` 永远够不着预算,摘要一次都不触发,级联断在第二环。

改成降到预算的 **8 成以下**才停(`DEMOTE_TO_RATIO=0.8`):一次挪一批,层 2 才攒得起来。这条不是什么精妙设计,是「循环终止条件要给出余量」——按边界停会让系统长期贴在边界上,下游每个依赖「远离边界」的触发器全都哑火。

顺带加了一条:**层 1 至少要留最后一条**,`while len(layer1_items) > 1`。层 1 空掉等于把用户刚说的话丢了,比超预算更糟。

### bug 3:日志里 `layer1=33 条 / 0 token`

`react.py` 直接构造 `LayerPlan(layer1=...)`,只塞了消息列表,`tokens_layer1` 停在默认值 0。日志出现自相矛盾的数,排查时最误导人。补 `plan_from_history()` 统一算 token。

### 一处测试改动的说明(不是「测试跟着代码改」)

`test_layer1_over_budget_demotes_and_moves_anchor` 原来断言 `plan.tokens_layer1 <= 20`。加了「层 1 至少留一条」之后这条不成立了(单条 63 token)。断言改成 `len(plan.layer1) == 1` 且留下的是最后一条——**验的是需求里没写、但必须成立的性质:最近那句话不许压**。原断言验的「不超预算」在极端配置下本来就不可能同时满足。

### bug 4:摘要任务没有防抖,同一批可能被压两遍

`schedule_summary` 原来只判「超预算就起任务」。压一段要一两秒,这期间用户完全可能再发一句:第二次触发时读的还是**同一个旧锚点**,于是同一段对话被压两遍、落两段重复梗概,而锚点只推到同一处——库里凭空多一条重复事实。

修法:模块级 `_running{conversation_id: task}` 去重 + `add_done_callback` 清理,清理时只清自己(任务结束时可能已经排了下一个,别把后来者抹掉)。补 `test_second_trigger_is_skipped_while_first_is_running`,顺带验「跑完必须放行」——去重表漏清等于让摘要从此再也不触发,这是去重方案最常见的坑。

## 2026-10-21 T6 只读接口与侧栏

### 关键产出

- `GET /api/v1/conversations?user_key=&limit=`:该用户全部会话,新的在前,带首问预览、条数、「已摘要」标记。
- `GET /api/v1/conversations/{id}/messages?user_key=`:回载历史**原文**(不是梗概),带 `summarized` 标记。
- 前端:`#conv-sidebar` + `loadConversations()` / `renderConversations()` / `openConversation()`;`done` 事件与「新会话」按钮都会刷新侧栏。

### 三个定下来的点

**参数叫 `user_key` 而不是 `session_id`。** 查询是按会话归属键做的,叫 `session_id` 会让人以为能查别人;接口文档里写明「本项目没有用户体系,`user_key` 就是聊天接口的 `session_id`」(README 已知限制)。

**切会话必须清掉上一会话的订单选择状态。** `openConversation` 里三行:`conversationId = id`、`pendingNewConversation = false`、`selectedOrderId = null`。不清 `selectedOrderId` 的话,切过去之后第一次点「申请退款」会把上一会话选的订单号带进去——这是最难受的一类 bug:界面看着对,单子下错了。

**侧栏列表失败静默,打开历史失败报错。** 列表是背景信息,拿不到就当没有(整个窗口只剩聊天);点开历史是用户主动动作,静默会让人以为「这段对话丢了」。

## 2026-10-21 T7 验收:级联要真跑出来

### 关键产出

- `scripts/context_demo.py`:`--turns` / `--demo-config` / `--expect-cascade on|off`,自带 `CountHandler` 数降级次数、摘要 trigger/start/done/fail,以及 `model_ctx` / `history_ctx` 各打了几次。脚本自己起库、自己装配依赖,不用起服务。

### 两个环境坑(都不是代码 bug,但会让整轮验收白跑)

**向量库是文件锁,服务和脚本不能同时用。** 8010 的服务开着,脚本会拿到 `PermissionError: [Errno 13] Permission denied: data/devstack_milvus.db\LOCK`,而检索失败只打一行 WARNING,表现是「每轮都在拒答」——从结果看不出来是环境问题。解法两个:停服务,或者把向量库目录复制一份给脚本单独用(我选的后者,不动用户可能在用的服务)。

**`.env` 指向 MySQL,验收要覆盖成 SQLite。** 开发台配置(`DATABASE_URL=sqlite+aiosqlite:///./data/ch07.db`、`VECTOR_STORE_URI=./data/ch07_milvus.db`)在命令行前置,不写进 `.env`——`.env` 是给真库联调和用户自己跑用的。

**新库是空库,知识块得先补。** 第一版 45 轮里知识类提问全拒答,`gate_reason=no_hits`,看着像检索坏了。根因是 `data/ch07.db` 只有 CH07 新建的表,`knowledge_chunks` 是 0 行——向量检索命中了,但回 MySQL 取原文取不到,按「零命中」处理。补了 357 行(从 `devstack.db` 复制)才正常。

### 45 轮的第一轮结果:级联只走到一半

```
failures: 0    demotions: 15    summary_triggers: 0    anchors: (0, 337)
window=113 条(层 2 约 33 条,层 1 80 条)
```

`failures 0` 说明孤儿 tool 那条修住了(上一版是 4 次 `UPSTREAM_ERROR`)。但**摘要一次都没触发**。

不是触发逻辑坏了,是**45 轮在演示配置下还没把层 2 攒满**。一层一层算:层 1 预算 3947 token ≈ 80 条原文;每轮新增 2~3 条、约 40 token/条,层 1 涨到 3947 要十几轮;降级一次只挪 1~6 条进层 2,层 2 攒到 1693 token(约 50 条)要四十多次降级。45 轮里只降级 15 次、挪 21 条,层 2 停在 33 条 ≈ 1000 token。

**这条差异值得记下来:预算按「实测用量累加」和按「每轮上限预留」是两种口径。** 按实测,滑窗 5640 token 能装的实际轮数远多于按每轮 2000 token 预留算出来的 2.8 轮;好处是不浪费窗口,代价是「级联什么时候发生」取决于用户说了多少字,而不是聊了几轮。演示时想快看到就必须聊够长。

### 90 轮:完整级联跑出来了

```
failures: 0    demotions: 49    summary_triggers: 2    summary_done: 2
anchors: (513, 559)
summary trigger 会话 10 层2 约 1700 token > 预算 1693
summary done  会话 10 第1段 311 token,覆盖 msg 419~511,耗时 2447ms
summary trigger 会话 10 层2 约 1731 token > 预算 1693
summary done  会话 10 第2段 113 token,覆盖 msg 512~513,耗时 1192ms
```

这一段是需求里要的「完整级联」:层 1 满 → 降级 49 次 → 层 2 攒到刚过预算(1700 > 1693)→ 后台压成一段 311 token 的梗概 → 锚点推到 511 → 继续攒 → 第二次触发。**触发线卡在 1700/1693 这种个位数差额上,说明判据确实是「用量」而不是「大概齐」。**

第一段梗概的内容(节选):

> 涉及订单:1001 无线蓝牙降噪耳机×1 实付 399 元、待发货;1003 大容量双肩通勤包×1 实付 159 元、运输中;1005 …;1007 …。未解决:1001 发货进度待核实、1003 物流未查、1005 能否退及运费待人工核实…

四笔订单的事实与未解决诉求都在,寒暄没有。

### 一个靠梗概才暴露的 bug:时序指代指错了单

验收 2 的后半句是「靠梗概答对早期订单」。90 轮里第 56/76 两轮问「最开始那个订单后来怎么说」,模型都答成了**订单 1003**,而最早提到的是 1001。

查下来不是梗概的问题(梗概里 1001 排在最前,事实齐全),是**理解层看不到梗概**:`understand_query` 只吃 `history`(层 1 + 层 2),而早期内容早被压掉了,于是「最开始」只能从层 1 里零星的单号里猜——刚好最近提过 1003,就指到 1003 上。答出来的事实全对,但答非所问,这种错最难发现。

修法:`understand_query` 增加 `summary` 参数,prompt 里加两条——① 梗概进提示词;② 「最开始 / 第一次 / 早先」这类**时序指代**按梗概里订单出现的先后取最前面那一单。

验证用了一个定向探针(造一个「历史已压成梗概」的会话,直接问这句),答复变成《订单 1001 目前物流轨迹如下…》。这条同时说明**理解层的输入面必须和主力 Agent 一致**:两边都在长会话里工作,只给一边喂梗概,另一边就退化成猜。
